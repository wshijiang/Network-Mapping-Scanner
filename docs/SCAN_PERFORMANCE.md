## 服务识别

自适应回退原先对每个端点多次遍历全批证据，复杂度约为 O(端点数 × 证据数)。改为按 `(ip,port)` 一次建立摘要，再查找传输可达性、HTTPS 和 TLS 成功状态。探针顺序、预算、置信度、DoH 细化和失败 TLS 证书保留不变。

本地无网络 CPU 基准，Rust test 调试构建，11 次中位数：

| 端点数 | 修改前 | 修改后 | 比值 |
| --- | ---: | ---: | ---: |
| 512（默认批大小） | 22.823ms | 4.129ms | 5.5× |
| 4096（规模压力） | 1271.223ms | 32.511ms | 39.1× |

这里只测回退规划，不是网络扫描总时长。实际运行仍可能受目标超时、单 IP 限速、zgrab2、网页内容富化影响；本次没有调低超时或减少探针覆盖。

```bash
cargo test --lib benchmark_fallback_planning -- --ignored --nocapture
```

修改前基线为 `820658e`，将同一基准测试放入该版本可重跑；4096 端点是规划函数压力输入，不代表更改默认批大小。不同硬件和构建 profile 的数值不能直接比较。

## 上传调查与改动

- 上传原先为每批深拷贝最多 500 条观察（包含握手 JSON）；现直接借用缓存切片序列化，报文及断点边界一致。缓存只在服务端确认后推进批号。
- 成功 HTTP 响应原先只检查状态码就释放；响应体仍在传输时，HTTP/1 连接可能不能复用。现以流式方式读完确认体，累计上限 64KiB，沿用请求总超时。中途断线按可重试传输错误处理，仍使用原 upload_id/batch_index。回归测试使用延迟分片响应，验证两个批次复用一条 TCP 连接。
- `ResultBatchUploaded.elapsed_ms` 包括请求 JSON 编码、发送、服务端处理和确认体读取；`ResultUploadCompleted.elapsed_ms` 为本次 flush 总时长，`planning_ms` 单独记录批次划分时间。它们均不记录观察内容或凭据。续传时 `batch_count`/`observation_count` 仍表示整个缓存任务的规模。

500 条服务观察、每条 12000 字节 body、21 次中位数的“批次构造 + JSON 编码”本地基准：深拷贝 **103.470ms**，借用 **103.135ms**。差异很小，不能据此宣称端到端上传吞吐明显提高；JSON 编码在该调试构建中占主要开销。减少拷贝主要降低临时内存需求。

```bash
cargo test --lib benchmark_upload_preparation -- --ignored --nocapture
cargo test --lib upload
```

### 定位线上慢上传

按 task_id / upload_id / batch_index 对照扫描器日志与服务端 `ScanWriteStageCompleted` 的 `stage`、`duration_us`：

1. `planning_ms` 高：检查结果总量和握手/body 大小；分批规划会测量整个缓存的序列化大小。
2. 多个普通批次均慢：比较 `write_observation_bulk` 和 `write_execution_endpoints`，检查 Elasticsearch Bulk 延迟、重试、磁盘和副本确认；若服务端处理快而客户端耗时高，再检查链路带宽、TLS/代理和连接复用。
3. 仅最后一批慢：重点检查 `refresh_execution_indices`、`execution_summary` 和索引清单。最终批次必须等待刷新和精确统计，不能把这一时间全部归因于传输。
4. SQL 慢：搜索新鲜度已通过持久 outbox 异步处理；另见服务端 `docs/SCANNER_PERFORMANCE.md` 的查询前后比较。观察 outbox 的滞后和重试，而不是提高告警阈值掩盖问题。

本次没有取得生产链路的分阶段日志或端到端吞吐数据。尚不能判断生产慢上传主要来自带宽、ES 写入还是最终统计；测试证明的是缓存报文兼容、连接复用以及重试正确性。
